# 组织模块调整开发计划

> 根据当前组织模块实现及已确认的讨论结论整理。本文规划角色规则收口、组织管理入口与组织头像，不包含平台超管、组织邀请或批量成员操作。

## 1. 目标与范围

### 本期包含

- 统一角色语义：`owner / admin / member / viewer` 均为组织内角色；用户未加入组织时没有组织角色。
- 保留 viewer，前提是代码盘点确认的只读协作场景继续成立；明确 viewer 可查看的数据范围及对话权限。
- owner 转让后，原 owner 从当前实现的 admin 改为 member；新 owner 与 `organizations.owner_id` 同事务更新。
- 保留“我的组织”作为所有成员的浏览/切换入口；组织行按角色展示操作。
- 管理页复用现有设置和成员接口；新增组织头像字段、上传/移除能力及前端统一头像组件。
- 后端负责最终授权；无权限操作在前端隐藏只是界面呈现规则。

### 本期不包含

- 第二套全量组织列表；平台级全部组织管理或超管角色。
- 批量成员操作、软删除、组织邀请、组织配额。
- 将 viewer 定义为用户全局状态。

## 2. 现状差异盘点

当前代码已有组织创建、我的组织列表、组织切换、名称修改、成员添加/搜索、角色修改、移除成员、退出组织、所有权转让和解散；成员管理接口已有 owner/admin 的后端权限校验及相关集成测试。创建组织对任意已登录用户开放，创建者自动成为 owner。

角色在代码中已经是组织内角色：迁移预置四种角色，成员记录通过 `role_id` 关联；Agent、知识库等模块给 member/viewer 只读访问。需求文档第 2 节却将角色称为“用户角色”，需要修正概念并补全矩阵。目前执行记录模块拒绝 viewer 访问，须确认这是期望限制还是与只读协作目标不一致。

主要实现差异：

1. 所有权转让后旧 owner 当前降为 admin，目标规则要求降为 member。
2. 组织表、请求/响应模型、组织列表、设置页和切换器目前没有头像字段或上传功能。
3. 现有“我的组织”是卡片列表，具备创建和进入入口；管理入口需按 owner/admin 显示。搜索和“我管理的 / 我加入的”筛选尚未实现。
4. 成员搜索当前只支持邮箱；目标操作需要名称/邮箱搜索。
5. 前端有零散组织首字头像表现，需要盘点并收敛到统一“组织头像组件”。目前未发现 `logo` 字段命名，新增时直接使用 `avatar_key`，避免引入 logo 术语。

## 3. 页面与操作设计

### 3.1 我的组织列表

不新增第二套全量组织列表。“我的组织”保留为全员浏览与切换入口，列表仅包含当前用户加入的组织。顶部提供：

- 新建组织：所有已登录用户可见。
- 按名称搜索。
- 范围筛选：“我管理的”（owner/admin）与“我加入的”（全部成员）。

每行展示组织头像、名称、成员数、创建人/owner、加入时间或创建时间、本人角色及状态。所有角色可进入组织工作区；member/viewer 可退出；owner 需先转让或解散，不能直接退出。

owner/admin 行显示“管理”入口，进入对应组织的管理页；member/viewer 不显示该入口。owner 额外可从管理页发起所有权转让或解散。列表不承载平台级管理功能。

### 3.2 组织管理页

管理页只针对单个组织，分为“组织设置”和“成员管理”区域。优先复用 `/organizations/{id}/settings`、`/organizations/{id}/members` 现有路由与 API；如实际布局需要，可将两页并入同一页面的分区/标签，不另建重复数据接口。

| 操作 | owner | admin | member | viewer |
| --- | --- | --- | --- | --- |
| 进入组织工作区 | ✓ | ✓ | ✓ | ✓ |
| 退出组织 | —（先转让/解散） | ✓ | ✓ | ✓ |
| 管理入口与管理页 | ✓ | ✓ | — | — |
| 转让所有权 | ✓ | — | — | — |
| 解散组织（二次确认） | ✓ | — | — | — |
| 编辑名称/简介 | ✓ | ✓ | — | — |
| 上传/替换/移除组织头像 | ✓ | ✓ | — | — |
| 添加成员（admin/member/viewer） | ✓ | ✓（只可授予低于自身的角色） | — | — |
| 修改角色 | ✓ | ✓（不可操作同级/上级） | — | — |
| 移除成员（二次确认） | ✓ | ✓（不可移除 owner/admin） | — | — |
| 成员搜索（名称/邮箱） | ✓ | ✓ | — | — |
| 批量操作 | 本期不做 | 本期不做 | — | — |

admin 可添加 member/viewer、修改或移除 member/viewer；不可添加 admin、修改/移除其他 admin、触碰 owner。owner 可管理 admin/member/viewer，但不能通过普通成员添加入口指定 owner。转移所有权只能走专用操作。

### 3.3 确认与退出体验

- 移除成员、转移所有权、解散组织均要求确认；解散继续采用输入组织名匹配后才能提交。
- owner 退出按钮不显示，提示需先转让所有权或解散组织。
- 成功转让后刷新组织详情、成员列表、我的组织列表和当前用户组织信息；若当前操作者已降为 member，管理入口随角色更新隐藏。
- 任何直接调用 API 的越权操作均由服务端拒绝，不能依赖前端隐藏按钮。

## 4. 角色和权限规则收口

1. 需求文档第 2 节由“用户角色”改为“组织内角色”；增加用户未加入组织时无组织角色的说明。
2. 保留 viewer 为组织内只读角色，不在用户表新增全局角色。新增/修改角色仍只允许 `admin/member/viewer`，owner 只能通过转让产生。
3. 单独核对文档定义与代码实现，尤其是 viewer 对 Agent、知识库、执行记录、成员资料与对话的读取范围；文档明确说明执行记录当前对 viewer 禁止，需确认是否维持。
4. 权限校验继续由后端组织依赖和 Service 规则强制执行。关键业务操作在 Service 层防止绕过路径，例如批量能力未来引入时也必须复用目标角色层级规则。
5. 组织解散保持当前受控硬删除语义；按现有流程由 owner 执行并清理关联资源，不在本期加入软删除字段。

## 5. 组织头像设计

### 5.1 数据与 API

- `organizations.avatar_key`：可空字符串，存储对象键或相对路径，不存本机绝对路径或带临时签名的 URL。
- 新增迁移增加可空字段；旧组织不回填，空值由前端头像组件自动回退。
- 新增 `PUT /api/v1/organizations/{id}/avatar` 上传/替换接口和 `DELETE /api/v1/organizations/{id}/avatar` 移除接口，均仅允许 owner/admin。
- 组织详情与组织列表响应提供可用的头像地址或头像键。若存储适配层之后可能使用对象存储，优先由服务端映射为可访问 URL，避免前端理解存储后端。
- 移除头像后将字段置空并尽力清理旧文件；替换时先保存并校验新文件，更新数据库成功后再清理旧文件，避免失败时丢失当前头像。

### 5.2 文件验证与缓存

- 允许 JPG、PNG、WebP，上传体积不超过 5MB；服务端按文件内容识别格式，限制像素尺寸并重新编码，输出建议控制在 1MB 内。
- 仅接受正方形图像；客户端提供 1:1 裁剪和本地预览，服务端仍进行独立校验与规范化。
- 使用内容哈希生成文件名（必要时包含组织 ID 前缀），替换后键值变化；配合长缓存头避免旧图缓存问题。
- 本地存储实现沿用当前部署方式，但通过存储接口隔离读写；存储键不依赖宿主机路径。以后迁移对象存储不应改数据库语义。
- 上传/读取遵循组织数据访问策略，不能因头像而意外公开私有组织附件；部署时确认静态文件服务的访问边界。

### 5.3 前端统一组件

新增统一的“组织头像组件”，用于我的组织列表、组织切换器和组织管理页：

- 有头像时显示裁剪后的方形图片；加载失败时回退默认头像。
- 无头像时取组织名称首字，按名称稳定哈希选择背景色；不依赖组织名之外的可变状态。
- 创建/编辑头像提供 1:1 预览、上传进度与失败提示；owner/admin 可替换或移除，其他角色只读。
- 全仓盘点已有组织头像/`logo` 相关命名并统一为 avatar 语义；用户头像仍用现有 user avatar 字段，不与组织头像混淆。

## 6. 建议实施批次

### 批次 A：规则与文档

- 完成 viewer 数据范围盘点，确认执行记录只读规则及对话权限。
- 更新 V1 需求文档与组织模块设计文档中的角色语义、权限矩阵、转让降级规则和页面分工。
- 对照 API、Service、前端入口和现有集成测试，建立改动清单。

### 批次 B：后端规则与组织头像 API

- 修改 owner 转让：目标设 owner、原 owner 设 member、`organizations.owner_id` 同一事务更新。
- 新增 `avatar_key` 数据库迁移、模型和 schema 字段。
- 实现上传/替换/移除 API、服务端图像校验/重新编码、内容哈希命名、存储清理与 owner/admin 授权。
- 扩展组织列表/详情与成员搜索接口（名称/邮箱）；组织名搜索/角色范围筛选可在客户端对“我的组织”结果执行，数据量增长后再考虑服务端分页。

### 批次 C：前端组织管理体验

- 调整“我的组织”行操作：进入组织对所有角色可见；退出对非 owner 可见；管理仅 owner/admin；转让/解散仅 owner。
- 将现有设置区与成员管理区作为管理入口目标，按角色裁剪控件；复用现有接口。
- 组织列表增加名称搜索和“我管理的 / 我加入的”筛选。
- 成员搜索扩展为名称/邮箱；本期不开发批量操作。
- 建立统一组织头像组件并应用于列表、切换器、管理页；接入上传、替换、移除和预览流程。

### 批次 D：验证与发布

- 验证 owner 转让后原 owner 为 member 且失去管理权限；admin 无法修改同级/上级；仅 owner 可解散。
- 验证 viewer 的实际读取范围与矩阵一致，跨组织资源仍不可见。
- 验证旧组织 `avatar_key=NULL` 时 UI 正常显示首字头像；JPG/PNG/WebP 合法图像可上传，伪造格式、超尺寸、非方形及超 5MB 文件被拒绝。
- 验证头像替换后 URL/对象键变化、移除后回退默认头像、失败替换不影响旧头像。
- 验证 member/viewer 无法通过直接 API 请求修改头像、成员或组织设置。

## 7. 关键验收清单

- 用户未加入组织时没有全局角色；创建组织用户成为该组织 owner。
- 我的组织只列出当前用户所属组织；全部成员可搜索、筛选和进入工作区。
- 仅 owner/admin 看见管理入口；组织管理页不提供批量操作。
- 所有权转让事务后只有一名 owner，组织 `owner_id` 与 owner 成员关系一致，原 owner 降为 member。
- admin 只能管理低于自身层级的成员；owner/admin 权限由服务端执行。
- 解散组织仅 owner 可执行并有二次确认；移除成员、转让亦有确认。
- 新旧组织均能通过统一组织头像组件正确展示；旧数据无需回填。
- API/DB/前端统一使用 avatar 语义，不出现组织 `logo` 与 `avatar` 混用。
